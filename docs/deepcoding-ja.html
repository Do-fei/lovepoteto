エージェントが最初の一行を書く前に

deepcoding

読む手がかり

「動く試作品を作って」という依頼でも、空のプロジェクトと、長く育ててきた製品とでは事情が異なる。前者なら手を動かしながら方向を探れるが、後者ではエージェントが最初に見つけた例が変更全体を左右しかねない。ローレンが deepcoding と呼ぶのは、作業の順序を変えることだ。設計の余地があるうちに、実装の判断に関わる資料をモデルに渡す。

具体例を読み解く

ローレンは、useEffect を不適切に使う古いコンポーネントが数多く残る React のコードベースを例に挙げる。周辺のファイルを検索したエージェントには、積み重なった技術的負債がチームの慣習に見えてしまう。検索結果を全部渡すより、小さくても新しく、今の方針をよく表す実装例を一つ選ぶ方が役立つことがある。その例をなぜ信頼できるかを見極めるのも、エンジニアの判断だ。

準備にかかる手間をどう抑えたか

ローレンが当時作った Claude Code プラグインでは、独立したサブタスクで文書、過去の変更、チームの議論を調べ、足りない情報は質問して補った。主タスクに渡るのは、選び取った資料だ。ただし、この準備にも時間がかかる。そこで文章は手早い試作の余地も残している。依頼した本人にも、何を尋ねたいのかは、少し作ってみて初めて分かることがあるからだ。

編集ノート

手戻りが生じた変更を一つ選び、もっと早く言っておけばよかった一言を探してみよう。その言葉を関連するファイルやテストと一緒に依頼の冒頭へ移す。エージェントの判断がどの段階で変わるかを観察できる。
